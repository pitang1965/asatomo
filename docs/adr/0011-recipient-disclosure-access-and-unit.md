# ADR-0011: 受取人の開示画面のアクセスモデルと配信単位

- ステータス: Accepted
- 日付: 2026-07-26

## 背景（Context）

[[受取人]]が[[合言葉]]を入力して[[最後の伝言]]を復号・閲覧する**本番の開示画面（(C)）が未実装**だった。これが無いと伝言は書けても誰も受け取れず、差別化の核（[[最後の伝言]]）が端から端まで成立しない。

上流はすでに揃っている: [[死亡認定]]の T5 開示（cron）・開示メール送信（notifier）は実装済みで、通知メールは本番リンクを載せている。欠けているのは*最後の一区間*——リンクの先の公開ルートと、その認可・開示ゲートだった。

この設計には既存の制約が効く:

- **受取人はアカウントを持たないことがある**（純Web受取人＝メールのみ、`connections.externalEmail`）。ゆえに現行の全ルートが要求する「認証済み actorUserId」を**そもそも通せない**（ADR-0002 の「メールだけの非技術者の受取人でも成立」）。
- **ゼロ知識**（[ADR-0002](0002-final-message-encryption-key-custody.md)）: サーバは暗号文しか持たず、合言葉も鍵も保持しない。復号は端末側。
- **開示は死亡認定の成立でゲートする**（[ADR-0001](0001-death-certification-authorization-model.md) 不変条件C・不可逆の終点）。
- **受取人は生前、自分が受取人であることを知らされない**（開示までの沈黙。CONTEXT [[受取人]]）。

## 決定（Decision）

**1. 公開ルート＋capability URL＋状態ゲート（ログイン不要・経路統一）**

- 開示ルートは**ログイン不要の公開ルート**。認可は開示メールで届く**推測不能な `connectionId`**（capability）と、サーバー側の**開示ゲート**（その本人に `death_certifications.outcome='disclosed'` が存在すること）の2つだけで行う。
- **アカウント持ちの受取人にもログインを課さない**（経路を二分しない）。capability URL を全受取人で統一する。
- 根拠: ゼロ知識ゆえ URL は暗号文の**在り処を示すだけ**で、本当の秘密は合言葉。URL が漏れても読めるものは出ない。署名/期限トークンはサーバー側の秘密管理を増やし、ソロ開発・無料枠・放置耐性とゼロ知識に逆行する割に、合言葉が実質のゲートである以上得るものが小さい。

**2. 開示成立前は存在を隠す中立応答**

- 開示成立前・不正URL・削除済みを**区別のつかない単一の中立応答**（`unavailable`）にまとめる。理由を分岐させない（差分から存在の有無が漏れるため、3ケースは**完全に同一の応答**）。
- 「あなた宛に死後の伝言が用意されている」事実自体、本人の存命中に漏れると意図の漏洩・不安喚起になる（[[受取人]]の沈黙の約束）。ログインの有無を問わず中立にする。
- 実運用では開示メールは T5（開示時）にしか送られないため、成立前アクセスはほぼ発火しない異常系。よって中立化のUX代償はほぼゼロで、プライバシー保護だけが実在する。

**3. 配信単位は受取人（connection）ごと**

- ルートは **`/disclosure/{connectionId}`**（`messageId` を URL から外す）。
- その受取人宛で**開示成立済みの全伝言**を1画面に集約。合言葉は受取人ごとに1つ（`connections.passphraseHint` が示すモデル）なので、**合言葉を一度入力すれば**その受取人の全伝言の `wrappedDek` を同じ合言葉で順に解ける。
- 通知メールも**受取人ごとに1通**へ集約（従来の伝言ごと1通をやめる）。
- 根拠: 合言葉モデルがすでに受取人ごと。伝言ごとURLはこれと衝突し、同じ合言葉を何度も打たせ、弔いの最中にほぼ同一メールを複数送る。

**4. 実装の形（dispatch を通さない）**

- 公開 TanStack ルート `src/routes/disclosure.$connectionId.tsx` ＋ 公開 server function `fetchDisclosure`（`fetchInvitePreview` / `join.$token` と同型）。**認証必須が不変条件の `dispatch` ルート表は通さない**（あの表に公開例外を差し込むと、将来のルートがうっかり公開される foot-gun になる）。
- ゲートは新クエリ `resolveDisclosureForRecipient(db, connectionId)` の **WHERE に埋め込む**（別チェックにしない＝ゲート未成立なら行が返らず暗号文を取り出せない。TOCTOU なし）。返すのは最小限（差出人名・ヒント・暗号文・iv・wrappedDek）。暗号化見出しは返さない。
- 既存の `resolveDisclosure`（バッチ用・通知層）は役割が違うので温存。

**5. 合言葉入力は平文のみ（マスクトグルなし）**

- 受取人は最も非技術者寄り・一度きり・悲しみの最中。合言葉は「その受取人だけが知る答え」で使い回す資格情報ではなく、肩越し盗み見リスクも低い。入力欄をマスクしても手紙本文（復号後表示の別物）は守られない。将来 opt-in マスクは些末な追加で足せる。

## 結果（Consequences）

**正**

- メールだけの受取人でも成立し、全受取人で経路が統一される。ゼロ知識を保つ（サーバは暗号文のみ提供、URL 漏洩だけでは合言葉なしに読めない）。
- 開示成立まで受取人指定・伝言の存在を隠せる（本人の意図を守る）。
- 合言葉1回・受取人ごと1通で、多通ケースのUXが親切。
- 公開面が1ファイルに隔離され監査しやすい。

**負 / 要フォロー**

- **暗号ペイロードを返す公開ルート**は一見驚く。安全性は capability の推測不能性＋状態ゲートに依存する。将来「認証を足す」退行を防ぐため本ADRに記録。
- 中立 `unavailable` ページは、正規の早すぎるクリックには不親切になりうる。ただし正規クリックは開示成立後（メールは T5 送信）にしか起きず、実害はほぼゼロ。
- 通知層を「伝言ごと1通」から「受取人ごと1通」へ変更し、リンク形を `/message/{messageId}/{connectionId}` から `/disclosure/{connectionId}` へ変える必要がある。

## 検討した代替案（Alternatives considered）

- **署名付き/期限付きトークンを URL に埋める**: サーバー側の秘密管理を増やし、ゼロ知識・ソロ開発・放置耐性に逆行。合言葉が実質のゲートなので得るものが小さい。却下。
- **アカウント持ち受取人だけログイン必須**: 経路が二分し、メールだけの受取人が壊れる。却下。
- **成立前に「まだ開けません」と正直に伝える**: 本人の死ぬ前に受取人指定が漏れ、沈黙の約束を破る。却下。
- **配信単位を伝言ごとにする**: 多通ケースで重複メール・合言葉の複数回入力を生み、受取人ごとの合言葉モデルと衝突。却下。
- **`dispatch()` に認証例外を設けて通す**: 認証必須という不変条件を崩し、将来のルートを公開by-accidentにする foot-gun。却下。
